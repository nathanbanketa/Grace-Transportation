# Design baseline audit

Reviewed against `main` at `3408f19`. Chromium rendered the landing and driver routes at 390 × 844, 768 × 1024 and 1440 × 900. A local Supabase API fixture allowed sign-in, customer submission and a seeded request without touching real bookings. Conditional states beyond fixture coverage were inspected in source.

| Surface | Keep | Findings |
| --- | --- | --- |
| Public header, hero, services, about and footer | Dove-and-SUV mark, recognizable vehicle, DFW context, booking CTA, existing service and driver facts | The desktop vehicle reads clearly, but the bordered image and repeated service cards make the composition generic. Five similar service cards create a long mobile stack. Section prefaces and service icons repeat adjacent text. Mobile CSS removes Services and About navigation entirely. |
| Booking steps and conditional airport fields | Explicit labels, Central time, first-invalid focus and preserved values between steps | The progress row and step heading repeat the same information. The mobile form is long with limited grouping. Required fields are not identified before validation. Many errors collapse to the same generic sentence. The review uses the same emphasis for route, counts and contact information. |
| Booking pending, server error and receipt | Disabled submit, retryable errors, explicit pending language and focus on receipt | Submission progress is communicated through the disabled button label alone. Server error sits at the bottom of the review. A long UUID in the receipt needs a deliberate wrap treatment. Separate a saved request from a paid reservation visually and verbally. |
| Driver sign-in | Named fields, autocomplete, alerts and existing account checks | Reuses a generic admin panel instead of a deliberate sign-in layout. Invalid credentials and unavailable service have alerts. There is no explicit pending treatment. |
| Admin shell, Requests, Upcoming and History | Named destinations, active navigation, status text, refresh and alerts | On phones the header, live label, three count tiles and wrapped filter chips precede the queue. Filters, summary counts and cards compete for attention. On desktop the dashboard uses marketing display type and repeated boxed modules. Global `nav` rules also reach the driver shell. Tablet width retains the fixed phone nav. |
| Schedule | Central time, date controls, ride links and availability actions | Fourteen equally weighted day cards form a long mobile stack, including empty days. The block form precedes the calendar. Repeated nested controls obscure the distinction between viewing the agenda and changing availability. |
| Payments | Clear deposit, review and refund information, linked booking records | Summary cards compete with the payment list. Narrow equal-width tiles constrain longer labels and amounts. Empty history is styled like an ordinary content panel. |
| Booking details | Contact and direction links, route, timing, actions, editing, payment and audit data | Identically weighted panels put the price action below a long mobile details stack. The fixed bottom nav limits the usable form viewport. Read-only route details, edit inputs, payment status and activity need a clearer hierarchy. Error and empty messages are distributed across panels. Test long addresses, references and text scaling. |
| Shared feedback and fallback pages | Existing `role=alert` and status text, labeled controls, refresh fallback, reduced-motion rule | Feedback is split among several local styles. Keyboard focus largely relies on browser defaults. No dedicated admin loading, unexpected-error or not-found design is present. Push and unavailable-provider feedback needs the same pattern as other actions. |

## Verification coverage to carry into implementation

- Rendered baseline includes the home page, booking validation, airport fields, contact, review, submitted receipt, sign-in error, request list, booking details, schedule, history, upcoming and payments. The fixture covers representative content and empty views.
- Audit findings about submitting and failed requests, stale and conflicting actions, populated payment and availability states, refresh and push statuses, and error boundaries are source observations. Capture these during implementation with controlled fixtures. Verify WCAG contrast, keyboard use, zoom/reflow, real iOS and Android behavior where available, and the booking and authentication paths.
- Keep existing routes, field names, handlers, payment and notification semantics, and accessibility behavior. No application files were changed in this preparation stage.
